# Day 32: Persistent Storage with PostgreSQL & pgvector

Welcome to Day 32 of the roadmap! Today we tackled one of the most critical stages of the RAG pipeline: **Persistent Vector Storage**.

## The Problem: Ephemeral Data
In Day 31, we successfully utilized our concurrent worker pool to fetch mathematical vectors from the Google Gemini API. However, we were simply holding them in RAM and printing them to the terminal. When the Go program exited, the vectors disappeared. To search them later, we need them stored permanently on a hard drive.

## The Solution: PostgreSQL + pgvector
We chose **PostgreSQL** coupled with the **pgvector** extension. This allows us to store our document metadata right alongside the mathematical vectors, and perform blazing-fast similarity searches (cosine distance) directly in SQL.

### What was built:
1. **Docker Infrastructure (`docker-compose.yml`)**: We set up a local Postgres 16 instance with the `pgvector` extension pre-installed. We bound it to port `5433` to prevent conflicts with other local databases.
2. **The Storage Interface (`internal/storage/storage.go`)**: We defined a strict `Storage` interface. This senior-level design pattern ensures our core pipeline doesn't care if it's talking to Postgres, Pinecone, or Milvus—it just knows it can `SaveEmbeddings`.
3. **The Postgres Implementation (`internal/storage/postgres.go`)**: 
   - We utilized `github.com/jackc/pgx/v5` for high-performance database connections.
   - We utilized `github.com/pgvector/pgvector-go` to natively handle the vector types in Go.
   - We executed `CREATE EXTENSION IF NOT EXISTS vector` automatically on startup.
   - We used `pgx.Batch` to insert multiple vectors in a single network round-trip, optimizing throughput.

## The Edge Case: Dynamic Dimensions
During testing, we discovered that Google's `gemini-embedding-2` model generates vectors with exactly **3072 dimensions**, rather than the older standard of 768. 

Instead of hardcoding this new number and creating a brittle schema, we implemented **Dynamic Dimension Detection** in `main.go`. Before the database table is created, the Go code inspects the very first vector generated by the API, measures its length, and dynamically builds the SQL `CREATE TABLE` statement to match (e.g., `vector(3072)`). This makes our architecture incredibly robust and provider-agnostic!
